# 4.1 Setup der Entwicklungsumgebung

## 4.1.1 Zielsetzung und Anforderungen an Reproduzierbarkeit

Eine sorgfältig dokumentierte Einrichtung der Entwicklungsumgebung ist eine wesentliche Voraussetzung für die wissenschaftliche Belastbarkeit des Projekts. Reproduzierbarkeit gilt im akademischen Bereich als zentrales Qualitäts­kriterium [Peng 2011] und ist insbesondere bei Big-Data-Anwendungen kritisch, da unterschiedliche Versionen von Spark, Java oder Python zu signifikant abweichenden Laufzeiten oder gar funktionalen Fehlern führen können.

Aus diesem Anspruch ergeben sich folgende Anforderungen an die Dokumentation:

1. **Vollständigkeit**: Jeder Befehl, der zum Aufbau der Umgebung notwendig ist, muss aufgeführt sein.
2. **Versionsfestlegung**: Alle Softwarekomponenten werden mit expliziten Versions­nummern verankert.
3. **Plattformbeschreibung**: Die Eigenschaften der Ziel-Hardware (CPU, RAM, Disk) und des Betriebssystems werden erfasst.
4. **Verifikations­schritte**: Nach jeder Installations­phase werden Tests definiert, die das erfolgreiche Setup belegen.

Die folgenden Abschnitte beschreiben die Einrichtung der Ziel-VM. Die Einrichtung der lokalen Entwicklungs­umgebung auf einem macOS-System unterscheidet sich nur in den verwendeten Paketquellen (`brew` statt `apt`) und ist analog dokumentierbar.

## 4.1.2 Ziel-Hardware und Betriebssystem

| Eigenschaft          | Wert                                        |
|----------------------|---------------------------------------------|
| Virtualisierung      | Ubuntu Desktop / Server (gehostet im DHBW-Rechenzentrum) |
| Betriebssystem       | Ubuntu 24.04 LTS                            |
| CPU                  | 4 vCPUs                                     |
| Arbeitsspeicher      | 8 GB                                        |
| Festplattenkapazität | ca. 50 – 100 GB                             |
| Netzwerkzugriff      | Internet (für `apt`-Updates und Datendownload) |
| Administration       | `sudo`-Berechtigung für den Projektnutzer (`group6`) |

Diese Konfiguration ist für das Projekt grenzwertig dimensioniert: Die 8 GB RAM stehen einem Datensatz von etwa 0,65 GB Rohdaten gegenüber, der durch Spark während der Verarbeitung deutlich expandiert wird. Eine sorgfältige Spark-Konfigurations­wahl (vgl. Abschnitt 4.1.10 und Kapitel 4.5) ist daher erforderlich.

## 4.1.3 Zugriff per SSH und VSCode Remote-SSH

Der Zugriff auf die VM erfolgt vom lokalen Entwicklungs­rechner aus per SSH:

```bash
ssh group6@<vm-host>
```

Die Authentifizierung wird über einen öffentlichen Schlüssel realisiert, der einmalig in der Datei `~/.ssh/authorized_keys` auf der VM hinterlegt wird. Diese Methode ist sicherer als Passwort­authentifizierung und vermeidet wiederholte Passworteingaben.

Für die produktive Arbeit wird zusätzlich die **„Remote-SSH"-Erweiterung von Visual Studio Code** eingesetzt. Sie ermöglicht es, dass Editor und Versionsverwaltung lokal auf dem Entwicklungs­rechner laufen, während der eigentliche Code auf der VM ausgeführt wird. Dadurch kombiniert sich die Bedien­ergonomie einer modernen IDE mit den Ressourcen der Ziel-VM.

## 4.1.4 Aktualisierung des Betriebssystems

Vor der Installation projektspezifischer Pakete wird das System auf einen einheitlichen Patch-Stand gebracht:

```bash
sudo apt update && sudo apt upgrade -y
```

`apt update` aktualisiert die lokalen Paketindizes, `apt upgrade -y` installiert alle verfügbaren Aktualisierungen ohne Rückfrage. Dieser Schritt ist insbesondere auf einer frisch bereitgestellten VM wichtig, um Sicherheits­updates zu erhalten und Konflikte mit veralteten Abhängigkeiten zu vermeiden.

## 4.1.5 Installation der Systempakete

Im nächsten Schritt werden die für das Projekt benötigten System­pakete installiert:

```bash
sudo apt install -y openjdk-17-jdk python3-pip python3-venv git unzip wget
```

| Paket            | Version (Stand 2026-06) | Funktion im Projekt                              |
|------------------|-------------------------|--------------------------------------------------|
| `openjdk-17-jdk` | 17.0.19                 | Java-Laufzeit­umgebung für Spark                  |
| `python3-pip`    | aktuelle                | Python-Paketmanager                              |
| `python3-venv`   | aktuelle                | Modul zur Erstellung virtueller Python-Umgebungen|
| `git`            | 2.43.0                  | Versionskontrolle, Synchronisation mit GitHub    |
| `unzip`          | aktuelle                | Entpacken des heruntergeladenen Datensatz-Archivs|
| `wget`           | aktuelle                | Herunterladen des Datensatzes per Kommandozeile  |

Die erfolgreiche Installation wird anschließend verifiziert:

```bash
java -version       # erwartet: openjdk version "17.x.x"
python3 --version   # erwartet: Python 3.12.x
git --version       # erwartet: git version 2.x.x
```

In der konkret durchgeführten Installation ergaben sich die Versionen Java 17.0.19, Python 3.12.3 und Git 2.43.0.

## 4.1.6 Anlegen einer virtuellen Python-Umgebung

Um Konflikte zwischen den vom Betriebssystem genutzten Python-Paketen und den projektspezifischen Abhängigkeiten zu vermeiden, wird eine isolierte virtuelle Umgebung angelegt:

```bash
python3 -m venv ~/venv
source ~/venv/bin/activate
pip install --upgrade pip
```

Die Aktivierung der Umgebung muss in jeder neuen Shell wiederholt werden. Der aktivierte Zustand ist durch das vorangestellte `(venv)` im Terminal-Prompt sichtbar. Mit `pip install --upgrade pip` wird sichergestellt, dass eine aktuelle Pip-Version zur Verfügung steht, was insbesondere für die korrekte Auflösung der PySpark-Wheel-Abhängigkeiten relevant ist.

## 4.1.7 Installation der Python-Pakete

Die projekt­relevanten Python-Bibliotheken werden in der aktivierten virtuellen Umgebung installiert:

```bash
pip install pyspark==3.5.0 pandas matplotlib jupyter
```

Die explizite Version `==3.5.0` für PySpark ist Teil der bewussten Versions­pflege. Die übrigen Pakete werden in der jeweils aktuellen Version installiert, da hier keine spezifischen Versions­abhängigkeiten bestehen. Der Download­umfang liegt bei etwa 380 MB; auf der Ziel-VM wurde der Vorgang in unter zwei Minuten abgeschlossen.

Eine Verifikation der Installation kann durch Prüfung der Versions­nummer von PySpark erfolgen:

```bash
python3 -c "import pyspark; print('PySpark', pyspark.__version__)"
```

Die erwartete Ausgabe lautet `PySpark 3.5.0`.

## 4.1.8 Herunterladen des MovieLens-25M-Datensatzes

Der Datensatz wird in ein eigenes Verzeichnis außerhalb des Projektordners gelegt, da er aufgrund seiner Größe nicht in die Versions­kontrolle aufgenommen werden soll:

```bash
mkdir -p ~/data
cd ~/data
wget https://files.grouplens.org/datasets/movielens/ml-25m.zip
unzip ml-25m.zip
ls -lh ml-25m/
```

Das Archiv hat eine komprimierte Größe von etwa 250 MB; nach dem Entpacken liegen die Dateien mit insgesamt ca. 1,1 GB im Verzeichnis `~/data/ml-25m/` vor. Eine detaillierte Übersicht der enthaltenen Dateien findet sich in Kapitel 2.4.

## 4.1.9 Klonen des Projekt-Repositorys

Das im Vorfeld auf GitHub angelegte private Repository wird auf die VM geklont:

```bash
cd ~
git clone https://github.com/Nicobaumann21/Meene.git movie-recommender
cd movie-recommender
```

Da es sich um ein privates Repository handelt, wird beim ersten Klonen eine Authentifizierung verlangt. Hierfür kommt ein **Personal Access Token (PAT)** zum Einsatz, der über die GitHub-Weboberfläche generiert wird. Der Token wird als Passwort beim HTTPS-Login eingegeben; der GitHub-Benutzer­name bleibt unverändert.

Um den Token nicht bei jedem nachfolgenden `git pull` erneut eingeben zu müssen, wird die Credential-Helfer-Funktion aktiviert:

```bash
git config --global credential.helper store
```

Die Token werden dabei in der Datei `~/.git-credentials` im Klartext abgelegt. Auf einer privaten Studien-VM ist dies vertretbar; für produktive Umgebungen wäre stattdessen ein SSH-Key oder ein verschlüsselter Credential-Manager vorzuziehen.

## 4.1.10 Konfiguration von Spark für die Ziel-VM

Wegen der begrenzten Arbeitsspeicher­ausstattung der VM (8 GB) müssen die Spark-Konfigurations­parameter manuell gewählt werden. Die im Projekt eingesetzten Werte stützen sich auf die Empfehlungen der offiziellen Apache-Spark-Dokumentation [Apache Spark 2024] sowie auf empirische Tests:

| Parameter                       | Wert | Begründung                                                          |
|---------------------------------|------|---------------------------------------------------------------------|
| `spark.driver.memory`           | 6g   | Maximaler Speicher für den Treiber. 6 GB nutzen die VM weitgehend aus, lassen aber 2 GB für Betriebssystem und Hilfsprozesse frei. |
| `spark.driver.maxResultSize`    | 2g   | Grenze für Ergebnisgrößen, die an den Treiber zurückgeliefert werden. Auf 2 GB angehoben, da `count`-Operationen auf dem 25M-Datensatz größere Zwischen­ergebnisse erzeugen. |
| `spark.sql.shuffle.partitions`  | 100  | Anzahl der Partitionen für Shuffle-Operationen. Bei 4 vCPUs ergibt 100 ein günstiges Verhältnis von Parallelität und Overhead (Faustregel: 2–4× Anzahl Kerne, in Big-Data-Szenarien bis 50× zulässig). |

Diese Werte werden in der Pipeline (`src/pipeline.py`) als Kommandozeilen­argumente übergeben (vgl. Kapitel 4.5).

## 4.1.11 Start von Jupyter Notebook mit SSH-Port-Forwarding

Für interaktive Exploration und Präsentation wird ein Jupyter-Notebook-Server auf der VM gestartet. Da die VM nicht direkt im Netz öffentlich erreichbar ist, wird der Notebook-Port über SSH auf den lokalen Rechner weitergeleitet.

**Auf der VM:**

```bash
source ~/venv/bin/activate
cd ~/movie-recommender
jupyter notebook --no-browser --port=8888
```

Jupyter gibt nach dem Start eine URL aus, die einen Sitzungs-Token enthält, zum Beispiel:

```
http://localhost:8888/?token=abc123...
```

**Auf dem lokalen Entwicklungs­rechner (in einer separaten Terminal-Sitzung):**

```bash
ssh -L 8888:localhost:8888 group6@<vm-host>
```

Damit wird der Port 8888 der VM transparent auf den Port 8888 des lokalen Rechners weitergeleitet. Anschließend kann die zuvor angezeigte URL im lokalen Browser geöffnet werden; der Code wird weiterhin auf der VM ausgeführt, lediglich die Bedien­oberfläche läuft lokal.

## 4.1.12 Verifikation des Gesamt-Setups

Als abschließende End-to-End-Verifikation wird die Datenpipeline auf dem MovieLens-25M-Datensatz ausgeführt:

```bash
source ~/venv/bin/activate
cd ~/movie-recommender
python src/pipeline.py \
    --ratings ~/data/ml-25m/ratings.csv \
    --driver-memory 6g \
    --max-result-size 2g \
    --shuffle-partitions 100
```

Bei erfolgreichem Setup wird die Pipeline die 25.000.095 Bewertungen einlesen, bereinigen und in einen Train/Test-Split überführen. Die erwartete Gesamtlaufzeit liegt im Bereich von 80 – 110 Sekunden (vgl. konkrete Messungen in Kapitel 4.5).

Die korrekte Funktion der Pipeline und die Plausibilität der berechneten Kennzahlen (Zeilenanzahl, Split-Größen) bestätigen, dass alle Schritte des Setups erfolgreich abgeschlossen wurden.
