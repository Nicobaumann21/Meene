# 3.3 Technologie-Stack

## 3.3.1 Methodisches Vorgehen bei der Technologieauswahl

Die Auswahl der eingesetzten Technologien folgt einer Anforderungs-Ableitung aus den Projektzielen und nicht einer bloßen Sammlung verbreiteter Werkzeuge. Aus der Aufgabenstellung — Entwicklung eines Collaborative-Filtering-Empfehlungssystems, das einen Datensatz von 25 Millionen Bewertungen auf einer Single-Node-VM mit 8 GB RAM verarbeitet — ergeben sich folgende technische Anforderungen:

| Anforderung                                  | Implikation für die Technologieauswahl                            |
|----------------------------------------------|------------------------------------------------------------------|
| Verarbeitung größerer Datenmengen als RAM    | Out-of-Core-Verarbeitung mit automatischem Spill-to-Disk         |
| Effiziente Matrix­faktorisierung             | Vorhandene, ausgereifte ALS-Implementierung                      |
| Parallele Nutzung der 4 vCPUs                | Daten­parallelität auf Thread- oder Worker-Ebene                  |
| Reproduzierbarkeit der Umgebung              | Versionierbarer Stack mit klaren Paketabhängigkeiten              |
| Akademische Anschlussfähigkeit               | Etablierte, gut dokumentierte Werkzeuge                          |
| Kompatibilität zwischen lokaler und VM-Umgebung | Plattformunabhängige Laufzeit                                     |

Im Folgenden werden die ausgewählten Komponenten und ihre Begründungen dargestellt.

## 3.3.3 Apache Spark als Datenverarbeitungs-Framework

Apache Spark ist ein im Jahr 2010 ursprünglich an der UC Berkeley entwickeltes verteiltes Datenverarbeitungs-Framework [Zaharia et al. 2010]. Es löste den älteren MapReduce-Ansatz von Hadoop in vielen Anwendungsfällen ab, indem es Zwischenergebnisse im Arbeitsspeicher hält und so iterative Algorithmen — wie sie im maschinellen Lernen üblich sind — deutlich beschleunigt.

Für das vorliegende Projekt ist Spark aus folgenden Gründen geeignet:

- **In-Memory-Computing mit kontrolliertem Spilling**: Spark verarbeitet Daten primär im RAM, ist aber in der Lage, bei Speicherknappheit auf Disk auszulagern. Dadurch kann der 647 MB große Datensatz auch auf einer VM mit nur 8 GB RAM zuverlässig verarbeitet werden.
- **DataFrame-API**: Die DataFrame-Abstraktion bietet SQL-ähnliche Operationen (`select`, `filter`, `dropna`) und nutzt den **Catalyst Optimizer**, der Abfragepläne in mehreren Stufen optimiert (Predicate Pushdown, Column Pruning, Codegenerierung). Im Vergleich zur älteren RDD-API ergeben sich dadurch oft erhebliche Performanzgewinne ohne manuelle Optimierung.
- **Parallelisierung auf Aufgabenebene**: Spark partitioniert Daten automatisch und verteilt die Tasks auf alle verfügbaren CPU-Kerne. Auf der Ziel-VM mit 4 vCPUs ergibt sich bei der gewählten Konfiguration mit 100 Shuffle-Partitionen ein gutes Verhältnis von Parallelität und Verwaltungs­overhead.
- **Single-Node-Tauglichkeit**: Obwohl Spark für Clusterbetrieb entwickelt wurde, läuft es zuverlässig im sogenannten *local-Mode*, in dem Treiber und Executoren in einer einzigen JVM ausgeführt werden. Damit eignet es sich auch für die hier vorliegende Single-Node-Konstellation.

### Spark MLlib

Auf Spark setzt die **Machine-Learning-Bibliothek MLlib** auf, die eine Reihe verteilter Algorithmen für Klassifikation, Regression, Clustering und Empfehlungssysteme bereitstellt [Meng et al. 2016]. Für dieses Projekt ist insbesondere die Implementierung des **Alternating Least Squares (ALS)** relevant, die direkt auf den Algorithmus von Zhou et al. [2008] (entstanden im Kontext des Netflix-Prize-Wettbewerbs) zurückgeht. ALS schätzt für jeden Nutzer und jedes Item einen latenten Faktorvektor; das Produkt zweier solcher Vektoren approximiert die Bewertung. Die Schätzung erfolgt iterativ, indem abwechselnd die Nutzer- und die Item-Matrix bei jeweils festgehaltener anderer Matrix als lineares Optimierungs­problem gelöst werden — eine Vorgehensweise, die sich besonders gut parallelisieren lässt und damit ideal zu Sparks Programmiermodell passt.

## 3.3.4 PySpark als Sprachanbindung

Spark ist nativ in Scala geschrieben, bietet aber offiziell unterstützte APIs für Python (**PySpark**), R und Java. Für das vorliegende Projekt fiel die Wahl auf PySpark, weil:

- Python im akademischen Umfeld der mit Abstand verbreitetste Stack für Data-Science-Aufgaben ist;
- die Einbindung in Jupyter-Notebooks nativ unterstützt wird, was iteratives Experimentieren beschleunigt;
- die DataFrame-API zwischen PySpark und Pandas eine sehr ähnliche Semantik aufweist, sodass Wissen zwischen beiden Welten übertragbar ist;
- die für Bachelor-Studierende gängigen Lehr­materialien (DataCamp, Coursera, etc.) PySpark als Standard verwenden.

PySpark erzeugt zur Laufzeit eine **Py4J-Brücke** zur JVM, in der die eigentliche Spark-Engine ausgeführt wird. Der dadurch entstehende Serialisierungs­overhead ist bei DataFrame-Operationen vernachlässigbar, weil diese durch den Catalyst Optimizer in JVM-nativen Code übersetzt werden.

## 3.3.5 Java 17 als Laufzeitumgebung

Spark 3.5 unterstützt offiziell die Java-Versionen 8, 11 und 17. Da Java 8 sich der End-of-Life-Phase nähert und Java 11 zwischen den Long-Term-Support-Versionen liegt, wird **Java 17** als aktuelle LTS-Version gewählt. Konkret kommt die **OpenJDK-17.0.19**-Distribution zum Einsatz, weil sie:

- frei verfügbar und identisch in den Paketquellen von macOS (Homebrew) und Ubuntu (`apt`) vorliegt,
- keine kommerziellen Lizenz­bedingungen unterliegt (im Unterschied zur Oracle-JDK),
- in beiden Umgebungen denselben Patch-Stand erreicht und somit Reproduzierbarkeit der Laufzeit­bedingungen ermöglicht.

## 3.3.6 Python 3.11 / 3.12

Lokal kommt **Python 3.11.10** zum Einsatz, auf der Ubuntu-VM die mitgelieferte **Python 3.12.3**. Diese Differenz wurde bewusst akzeptiert, weil:

- PySpark 3.5.0 mit beiden Versionen funktional kompatibel ist;
- die Installation einer abweichenden Python-Version auf einer frischen Ubuntu-VM zusätzliche Komplexität (z. B. via `deadsnakes`-PPA) bedeuten würde, ohne einen substanziellen Mehrwert zu liefern;
- der Pipeline-Code keine versionsabhängigen Sprachmerkmale verwendet.

Sollte sich im Projektverlauf eine Inkompatibilität zeigen, kann auf der VM mittels `pyenv` jederzeit auf Python 3.11 zurückgewechselt werden.

## 3.3.7 Unterstützende Python-Bibliotheken

- **Pandas** [McKinney 2010]: Wird genutzt, um die finalen Spark-Ergebnisse (etwa Top-N-Empfehlungen pro Nutzer) bequem in tabellarischer Form weiterzuverarbeiten und in CSV oder Markdown auszugeben.
- **Matplotlib** [Hunter 2007]: Die de-facto Standard-Bibliothek für statische Visualisierungen in Python. Wird für Verteilungs­diagramme der Bewertungen sowie für die Darstellung der Modellgüte (z. B. RMSE über Hyperparameter-Sweeps) eingesetzt.
- **Jupyter Notebook**: Ermöglicht interaktive Spark-Sitzungen, ohne den vollständigen JVM-Start­overhead bei jedem Skriptaufruf neu zu verursachen. Über SSH-Port-Forwarding (siehe Kapitel 4.1) kann der auf der VM laufende Notebook-Server bequem im lokalen Browser bedient werden.

## 3.3.8 Diskussion verworfener Alternativen

Im Zuge der Technologieauswahl wurden mehrere naheliegende Alternativen geprüft und aus folgenden Gründen verworfen:

| Alternative                  | Hauptargument gegen den Einsatz                                                                                  |
|------------------------------|------------------------------------------------------------------------------------------------------------------|
| `scikit-learn` (allein)      | Verarbeitet Daten ausschließlich im Hauptspeicher; bei 25 Mio. Zeilen auf 8 GB RAM nicht praktikabel. Bietet zudem keinen ALS-Algorithmus. |
| `surprise`                   | Spezialisiert auf Empfehlungssysteme, jedoch reine In-Memory-Bibliothek ohne Parallelisierung; bricht bei MovieLens 25M auf der Ziel-VM zuverlässig mit `MemoryError` ab. |
| TensorFlow Recommenders      | Deep-Learning-Framework; benötigt für vergleichbare Ergebnisse deutlich höhere Hardware-Ressourcen (GPU) und überschreitet den Umfang einer Projekt­arbeit. Klassisches CF bleibt für die Aufgabenstellung ausreichend. |
| Dask                         | Bietet zwar verteilte DataFrame-Verarbeitung, jedoch deutlich weniger ausgereifte ML-Bibliothek als Spark MLlib. Insbesondere existiert keine produktionsreife ALS-Implementierung. |
| Hadoop MapReduce             | Aufgrund der Disk-zentrierten Verarbeitung für iterative ML-Algorithmen rund eine Größenordnung langsamer als Spark [Zaharia et al. 2010]. |

## 3.3.9 Reproduzierbarkeit und Versionspflege

Sämtliche Versionen sind explizit gepinnt; Spark, PySpark und Java sind in beiden Umgebungen identisch. Lediglich die Python-Patch-Version unterscheidet sich (siehe oben). Die vollständige Installationsanleitung befindet sich in [`docs/4.1-setup.md`](4.1-setup.md). Damit ist gewährleistet, dass alle Ergebnisse — sowohl die in Kapitel 4 dargestellten Laufzeiten als auch die später folgenden Modellgüte­kennzahlen — auf einem beliebigen vergleichbaren System reproduziert werden können.
